# План разработки Ghostlink

Цель — один аккаунт на любом наборе устройств: **Android, iPhone, macOS, Windows**.
Ограничения: только бесплатный тариф Firebase **Spark** (без Cloud Functions), без телефона и почты пользователя.

Как устроен проект — в [ARCHITECTURE.md](ARCHITECTURE.md), почему так — в [adr/](adr/).

**Как читать план.** Этап — это GitHub Milestone, пункт `N.M` — Issue и один PR (ветка `feat/N.M-…`). У каждого этапа есть критерий «готово, когда»: этап закрыт, только когда он выполнен и CI зелёный.

## Этап 1. Привязка устройств на Android — ✅ готово

Скрытый аккаунт, привязка по QR, экран «Устройства», ключ восстановления, миграция анонимных аккаунтов (`4ccd305`). Проверено на Firebase Emulator и на настоящем проекте `ghostlink-7ffc8`: два устройства привязываются, удаление устройства выкидывает второе, переписка идёт в реальном времени.

Хвосты переходят в этап 2: подтверждение входа камерой реального телефона, бейдж непрочитанного, вход через Google.

## Этап 2. Инженерный фундамент и разведка — ✅ готово

Сначала делаем из проекта «настоящий» репозиторий, пока он маленький. Потом проверяем главный риск миграции.

**2a. Фундамент (на текущем Android-модуле)**
1. GitHub-репозиторий, защита `main`, шаблоны Issue и PR, Milestones 2–7, доска Projects.
2. CI: сборка, unit-тесты, Android lint на каждый PR.
3. Статический анализ: spotless + ktlint, detekt с baseline; обязательны в CI.
4. Тесты правил Firestore (`firebase/test`, `@firebase/rules-unit-testing`) на эмуляторе в CI. Они заменяют ручной `approve.js`.
5. Окружения: второй Spark-проект `ghostlink-dev`, флейворы `demo` / `dev` / `prod`, конфиги из секретов CI.
6. Renovate, Kover-отчёт покрытия, Conventional Commits + CHANGELOG.
7. Хвосты этапа 1: бейдж непрочитанного проверен в демо-режиме; Google-вход убран (#16) — восстановление только ключом. Подтверждение входа камерой реального телефона перенесено в 4.2.
8. Ответы на сообщения — первый продуктовый PR через новый процесс (Issue → ветка → CI → тесты правил → ревью). Поле `replyTo { id, senderId, preview }` в сообщении, правило с проверкой длины `preview` и тест правила, свайп по сообщению и плашка над полем ввода, цитата в пузыре с переходом к исходному сообщению.
   Позже: меню по долгому нажатию, как в Telegram, — «Ответить», «Копировать», а для своих сообщений «Изменить» (отметка «изменено», `editedAt`) и «Удалить» у обоих участников: на месте сообщения остаётся курсивная отметка «Сообщение удалено» (`deletedAt`), цитаты на него тоже её показывают. Свайп убран; протяжка ленты вниз прячет клавиатуру.

**2b. Разведка KMP (1–2 дня) — ✅ готово, итог в [ADR 0006](adr/0006-gitlive-on-jvm.md). Прототип лежит в `spike/ios/` в `main`: iOS и десктоп на общем Compose Multiplatform, отдельная Gradle-сборка вне основного CI.**
9. Минимальный KMP-прототип: вход по паролю и слушатель коллекции Firestore на Android, iOS-симуляторе и JVM против эмулятора.
10. Тот же прототип: `cryptography-kotlin` ECDH/HKDF/AES-GCM, шифротекст от текущего Android-кода расшифровывается на JVM и iOS.
11. Итог — ADR 0006: GitLive на JVM подходит, или десктоп уходит на REST + polling.

**Готово, когда:** любой PR в `main` проходит lint, тесты и тесты правил; есть dev-проект; ADR 0006 принят; ответы на сообщения прошли весь путь от Issue до `main`.

## Этап 3. Модули и Kotlin Multiplatform (Android остаётся рабочим)

Порядок выбран так, чтобы после каждого PR приложение собиралось и работало. Сначала разделяем на модули внутри Android, потом переводим модули на KMP.

1. `build-logic` с convention-плагинами, обновление Kotlin, AGP и Compose до актуальных версий.
2. `core:model`: перенос моделей; `value class` для id, `Instant` вместо `Long`, `Platform` enum, `GhostlinkError`.
3. `core:domain`: интерфейсы репозиториев и use case из ARCHITECTURE.md. ViewModel переходят на use case.
4. `core:testing` (фейки из `InMemoryBackend`) и `core:demo` (бот). Тесты ViewModel работают на фейках.
5. `core:crypto` на `cryptography-kotlin` + общие test vectors; старый `java.security`-код удаляется.
6. `core:firebase` + `core:data`: DTO, мапперы, реализации на GitLive, перевод ошибок в `GhostlinkError`, интеграционные тесты против эмулятора.
7. Hilt → Koin, `KoinModulesTest`.
8. `core:designsystem`, `core:ui`; ресурсы → Compose Resources.
9. `feature:*`: экраны по модулям, UiState/Action/Effect, навигация через `NavGraphBuilder`-расширения.
10. `core:platform`: `expect/actual` для `SecureStore`, `DeviceInfo`, `AppLifecycle`, `QrScanner`, `DeepLinks`.
11. Проверка графа модулей в CI; `app` → `apps:android`.

**Готово, когда:** Android работает как до миграции (прогон Maestro-сценариев: регистрация, привязка, друг, чат); все тесты в `commonTest`; `feature:*` не зависят от `core:data`.

## Этап 4. iOS

1. `apps:ios`: Xcode-проект, `ComposeUIViewController`, Firebase через SPM, shared-фреймворк.
2. `QrScanner` на AVFoundation, разрешение камеры; `SecureStore` на Keychain. Здесь же проверка из 2.7: iPhone камерой подтверждает вход нового устройства (на эмуляторе Android сканер с виртуальной камерой не работает).
3. URL-схема `ghostlink://`, безопасные отступы, клавиатура, жест «назад».
4. Maestro-сценарии на iOS-симуляторе в CI.
5. Crashlytics на Android и iOS (перенесено из этапа 7): падения на новой платформе видны сразу, а не после релиза.

**Готово, когда:** iPhone в одном аккаунте с Android; камера добавляет друга и подтверждает вход; падения с обеих платформ приходят в Crashlytics.

## Этап 5. Десктоп — macOS и Windows

1. `apps:desktop`: окно, адаптивная раскладка (список слева, чат справа при ширине > 840 dp).
2. Вход только через привязку: десктоп показывает QR, телефон сканирует.
3. `SecureStore` на `java-keyring` (macOS Keychain, Windows Credential Manager).
4. Друзья: показать свой QR или вставить ссылку `ghostlink://add/…`; регистрация схемы `ghostlink://` в ОС.
5. Трей и системные уведомления, пока приложение запущено.
6. Упаковка `.dmg` (arm64 + x64) и `.msi` через `nativeDistributions`, сборка в CI.

**Готово, когда:** Mac и Windows (или VM) привязываются к телефону (Android или iPhone) и переписываются в реальном времени.

## Этап 6. Push-уведомления и медиа (Cloudflare Worker + Backblaze B2, бесплатно и без карты)

1. `DeviceDto.pushToken` + правила + тесты правил.
2. `push-worker`: проверяет Firebase ID-токен, читает токены получателя, шлёт FCM HTTP v1. Ключ сервис-аккаунта лежит только в секретах Worker. Лимит частоты против спама.
3. `SendMessageUseCase` вызывает Worker; ошибка Worker не мешает отправке сообщения.
4. Android — FCM; iOS — FCM поверх APNs (нужен ключ APNs); десктоп — без push.

Firebase Storage для новых проектов требует Blaze, а Cloudflare R2 включается только с привязанной картой. Поэтому файлы лежат в приватном бакете Backblaze B2 (регистрация без карты), а доступ к ним выдаёт тот же Worker. Без карты B2 не выставляет счёт, а упирается в лимиты аккаунта: 10 ГБ хранилища, 1 ГБ скачивания в сутки, 2 500 скачиваний (класс B) и 2 500 служебных вызовов (класс C) в сутки. Бакет хранит только последнюю версию файла, иначе удалённые файлы продолжают занимать место.

5. `MediaStore` в `core:domain` (загрузить, получить ссылку на скачивание, удалить), реализация через Worker в `core:data`, фейк в `core:testing`. Экраны и сообщения не знают про B2: переезд на другое хранилище меняет одну реализацию.
6. Worker: проверяет Firebase ID-токен и членство в чате, выдаёт подписанные URL B2 на загрузку и скачивание с коротким сроком жизни; ключ приложения B2 с доступом только к бакету медиа лежит в секретах Worker; лимит размера файла и частоты.
7. `ImagePicker` в `core:platform` (Photo Picker на Android, PHPicker на iOS, диалог файла на десктопе) и сжатие на клиенте: фото до 1280 px и превью около 320 px отдельными файлами. Лента качает только превью, полный размер — при открытии. Скачанное кэшируется на диске: лимит 2 500 скачиваний в сутки на весь аккаунт B2 теснее, чем лимит трафика.
8. Сообщение с вложением: поле `attachment { key, thumbKey, type, size, width?, height? }` + правила + тесты правил; превью в пузыре, просмотр на весь экран.
9. Фото профиля: `users/{uid}.avatar { key, version }` + правила + тесты правил; загружается через тот же `MediaStore`, Worker отдаёт аватар любому вошедшему; клиент перекачивает его только при смене `version`.
10. Удаление: вложение удалённого или исчезнувшего сообщения и старый аватар удаляются из B2 (клиент вызывает Worker; без Blaze нет серверных триггеров).
11. Исчерпанный лимит B2: Worker отвечает понятной ошибкой, клиент показывает «Фото временно недоступно», текст переписки работает как обычно. Оповещения Caps & Alerts на 75% и 100% приходят владельцу проекта на почту.

**Готово, когда:** сообщение будит закрытое приложение на Android (и на iOS, если есть Apple Developer); фото, отправленное с одной платформы, открывается на остальных; собеседник видит фото профиля; при исчерпанном лимите B2 переписка продолжается без фото.

## Этап 6.5. Готовность к настоящим пользователям

То, без чего приложение отклонят в App Store и Google Play или без чего оно сломается при первых десятках пользователей.

1. Блокировка и жалоба (правило Apple 1.2): `users/{uid}/blocked/{otherUid}`, правила запрещают заблокированному писать в личный чат и добавлять в группы, тесты правил; заблокированный чат пропадает из списка. Жалоба — документ `reports/{id}`, который читает только владелец проекта в консоли.
2. Удаление аккаунта в приложении (Apple 5.1.1(v), Google Play): удаляются профиль, устройства, `chatPrefs`, свои сообщения помечаются удалёнными, затем удаляется аккаунт Firebase на всех устройствах.
3. Минимальная версия: документ `config/app` с `minVersion` по платформам, экран «Обновите приложение». Нужен до того, как ужесточать `firestore.rules`, иначе старые клиенты ломаются молча.
4. Квоты Spark (20 000 записей и 50 000 чтений в сутки): heartbeat присутствия реже и только при открытом приложении, троттлинг «печатает…», расчёт расхода на одного активного пользователя в ARCHITECTURE.md.
5. Пагинация ленты: сейчас загружаются последние 300 сообщений, старые подгружаются при прокрутке вверх.
6. Политика конфиденциальности (страница на GitHub Pages) и описание Data Safety для Play.

**Готово, когда:** заблокированный пользователь не может написать (проверено тестом правил); аккаунт удаляется из приложения; старая версия видит экран обновления; при 50 активных пользователях в день расчёт укладывается в квоты Spark.

## Этап 8. Сквозное шифрование (E2E)

Ключ аккаунта уже одинаковый на всех устройствах (его передаёт привязка), поэтому из него выводится постоянная пара ключей аккаунта, и синхронизировать ключи между устройствами не нужно. Цена простоты — нет forward secrecy: утечка ключа аккаунта раскрывает всю переписку. Это не протокол Signal, и README должен говорить об этом прямо.

1. `core:crypto`: пара X25519 из ключа аккаунта через HKDF; публичный ключ в `users/{uid}.publicKey` + правила + тесты правил; test vectors для всех платформ.
2. Личные чаты: ключ чата = ECDH двух публичных ключей → HKDF; `text`, `replyTo.preview` и `lastMessage` шифруются AES-256-GCM, id сообщения входит в AAD.
3. Группы: ключ группы создаёт админ и раздаёт участникам, зашифровав ключом личного чата с каждым; при удалении участника ключ меняется.
4. Вложения из этапа 6 шифруются на клиенте до загрузки в B2.
5. Проверка собеседника: код безопасности (отпечаток публичных ключей) в профиле, сравнение при встрече или по QR.
6. Переход: старые сообщения остаются открытыми и помечаются; push показывает «Новое сообщение» без текста.

**Готово, когда:** в консоли Firestore и в B2 нет открытого текста новых сообщений и файлов; переписка читается на всех платформах аккаунта; коды безопасности двух собеседников совпадают.

## Сознательные ограничения
- До этапа 8 нет сквозного шифрования (E2E), а в этапе 8 оно без forward secrecy.
- Нет звонков: для WebRTC нужен TURN-сервер, бесплатно надёжно не поднять.
- Отзыв отдельного устройства мягкий; жёсткий — только «выйти на всех устройствах» (смена пароля).
- На десктопе нет push, только уведомления запущенного приложения.
- Медиа живут в бесплатных лимитах B2: когда суточный лимит исчерпан, фото не грузятся до следующих суток.
