# План разработки Ghostlink

Цель — один аккаунт на любом наборе устройств: **Android, iPhone, macOS, Windows**.
Ограничения: только бесплатный тариф Firebase **Spark** (без Cloud Functions), без телефона и почты пользователя.

Как устроен проект — в [ARCHITECTURE.md](ARCHITECTURE.md), почему так — в [adr/](adr/).

**Как читать план.** Этап — это GitHub Milestone, пункт `N.M` — Issue и один PR (ветка `feat/N.M-…`). У каждого этапа есть критерий «готово, когда»: этап закрыт, только когда он выполнен и CI зелёный.

## Этап 1. Привязка устройств на Android — ✅ готово

Скрытый аккаунт, привязка по QR, экран «Устройства», ключ восстановления, миграция анонимных аккаунтов (`4ccd305`). Проверено на Firebase Emulator и на настоящем проекте `ghostlink-7ffc8`: два устройства привязываются, удаление устройства выкидывает второе, переписка идёт в реальном времени.

Хвосты переходят в этап 2: подтверждение входа камерой реального телефона, бейдж непрочитанного, вход через Google.

**Готово, когда:** Android работает как до миграции (прогон Maestro-сценариев: регистрация, привязка, друг, чат); все тесты в `commonTest`; `feature:*` не зависят от `core:data`.

## Этап 6. Push-уведомления и медиа (Cloudflare Worker + Backblaze B2, бесплатно и без карты)

1. `DeviceDto.pushToken` + правила + тесты правил.
2. `push-worker`: проверяет Firebase ID-токен, читает токены получателя, шлёт FCM HTTP v1. Ключ сервис-аккаунта лежит только в секретах Worker. Лимит частоты против спама.
3. `SendMessageUseCase` вызывает Worker; ошибка Worker не мешает отправке сообщения.
4. Android — FCM; iOS — FCM поверх APNs (нужен ключ APNs); десктоп — без push.

Firebase Storage для новых проектов требует Blaze, а Cloudflare R2 включается только с привязанной картой. Поэтому файлы чатов лежат в приватном бакете Backblaze B2 (регистрация без карты), а доступ к ним выдаёт тот же Worker. Без карты B2 не выставляет счёт, а упирается в лимиты аккаунта: 10 ГБ хранилища, 1 ГБ скачивания в сутки, 2 500 скачиваний (класс B) и 2 500 служебных вызовов (класс C) в сутки. Бакет хранит только последнюю версию файла, иначе удалённые файлы продолжают занимать место.

5. `MediaStore` в `core:domain` (загрузить, получить ссылку на скачивание, удалить), реализация через Worker в `core:data`, фейк в `core:testing`. Экраны и сообщения не знают про B2: переезд на другое хранилище меняет одну реализацию.
6. Worker: проверяет Firebase ID-токен и членство в чате, выдаёт подписанные URL B2 на загрузку и скачивание с коротким сроком жизни; ключ приложения B2 с доступом только к бакету медиа лежит в секретах Worker; лимит размера файла и частоты.
7. `ImagePicker` в `core:platform` (Photo Picker на Android, PHPicker на iOS, диалог файла на десктопе) и сжатие на клиенте: фото до 1280 px и превью около 320 px отдельными файлами. Лента качает только превью, полный размер — при открытии. Скачанное кэшируется на диске: лимит 2 500 скачиваний в сутки на весь аккаунт B2 теснее, чем лимит трафика.
8. Сообщение с вложением: поле `attachment { key, thumbKey, type, size, width?, height? }` + правила + тесты правил; превью в пузыре, просмотр на весь экран.
9. Фото профиля — в Firestore, не в B2: аватары скачивают чаще всего (список чатов, друзья, шапка чата), и в B2 они съели бы лимит скачиваний раньше фото. Картинка 256×256 (20–40 КБ) лежит в `avatars/{uid}.data` (`bytes`), в `users/{uid}` — только `avatarVersion`: документ профиля часто меняется из-за `online`/`lastSeen`, и картинка в нём скачивалась бы заново при каждом обновлении. Читает любой вошедший, пишет только владелец, размер ограничен правилами (до 64 КБ) + тесты правил; клиент перекачивает аватар только при смене `avatarVersion`. Worker не нужен, поэтому пункт можно сделать раньше остального этапа.
10. Удаление: вложение удалённого или исчезнувшего сообщения удаляется из B2 (клиент вызывает Worker; без Blaze нет серверных триггеров).
11. Исчерпанный лимит B2: Worker отвечает понятной ошибкой, клиент показывает «Фото временно недоступно», текст переписки работает как обычно. Оповещения Caps & Alerts на 75% и 100% приходят владельцу проекта на почту.

**Готово, когда:** сообщение будит закрытое приложение на Android (и на iOS, если есть Apple Developer); фото, отправленное с одной платформы, открывается на остальных; собеседник видит фото профиля; при исчерпанном лимите B2 переписка продолжается без фото.

## Этап 6.2. Привычные функции мессенджера

То, что пользователь ждёт от любого мессенджера. Почти всё укладывается в Firestore: новые поля, правила и тесты правил, без новых сервисов.

1. Реакции: `reactions.{uid}` — один эмодзи от каждого участника в документе сообщения. Правила разрешают участнику менять только свой ключ, длина строки ограничена; тесты правил. Долгое нажатие на сообщение, счётчики под пузырём.
2. Пересылка: новое сообщение с `forwardedFrom { name }` без ссылки на исходный чат (получатель может в нём не состоять) + правила + тесты правил. Файлы B2 привязаны к чату (`{projectId}/{chatId}/…`), и Worker выдаёт их только участникам, поэтому Worker получает `POST /media/copy`: копирует файл в новый чат внутри B2 (служебный вызов класса C), клиент заново ничего не загружает.
3. Закреплённое сообщение: `chats/{id}.pinnedMessage { id, senderId, preview }`; в группе закрепляет владелец, в личном чате — любой из двоих; правила + тесты правил. Плашка над лентой, нажатие прокручивает к сообщению.
4. Упоминания в группах: `mentions: [uid]` в сообщении, правила требуют, чтобы это были участники чата; подсказка участников после `@`. Чат с упоминанием отмечается «@» в списке даже с выключенным звуком; push (6.2) будит при упоминании и в заглушённом чате.
5. Поиск: по сообщениям открытого чата — на клиенте, по загруженной истории, догружая старые страницы (пагинация из 6.5); по названиям чатов и друзьям — в списке чатов. Серверного поиска нет намеренно: после E2E (этап 8) сервер текст не видит.
6. Черновики: недописанный текст хранится локально на устройстве для каждого чата, не в Firestore — набор текста не тратит квоту записей Spark. В списке чатов — «Черновик: …».
7. Избранное: чат с самим собой, `chats/{uid}` с `type: saved` и `members: [uid]` + правила + тесты правил. Всегда вверху списка; удобен для заметок и переноса фото и текста между своими устройствами. Фото работают через тот же Worker: проверка членства в чате проходит без изменений.
8. Архив: `chatPrefs.archivedAt`, отдельно от `hidden` (`hidden` — «удалён у себя», чат возвращается с новым сообщением); архивный чат остаётся в архиве и не входит в счётчик непрочитанных. Строка «Архив» вверху списка чатов.

Голосовые и видеокружки идут после push (6.2): запись → сжатие → B2 → проигрывание. Голосовые раньше кружков: тот же путь без камеры и примерно в 10 раз легче по трафику, на них отлаживается вся цепочка.

9. Голосовые сообщения: запись по удержанию кнопки (до 5 минут), AAC/Opus около 24 кбит/с (~180 КБ в минуту), `attachment.type = voice` с `duration` и волной громкости (несколько десятков значений прямо в сообщении, без отдельного файла) + правила + тесты правил. `AudioRecorder` и `AudioPlayer` в `core:platform`; на десктопе запись через `javax.sound`. Worker принимает тип `voice` со своим лимитом размера.
10. Видеокружки: только Android и iOS (у Compose Desktop нет API камеры), на десктопе — превью и проигрывание. Круглое превью камеры, запись по удержанию до 60 секунд; H.264 384×384 около 600 кбит/с (2–3 МБ за 30 секунд) и отдельное превью первого кадра, как у фото. `VideoRecorder` в `core:platform` (CameraX + MediaCodec на Android, AVFoundation на iOS), проигрывание в ленте через ExoPlayer и AVPlayer, звук по нажатию. Скачанное кэшируется на диске. Это самый дорогой для лимита B2 тип: 1 ГБ скачиваний в сутки — примерно 400 первых просмотров кружков на весь аккаунт, поэтому при исчерпанном лимите — «Видео временно недоступно», как у фото (6.11).

**Готово, когда:** между Android и iOS работают реакции, пересылка с фото, закреплённое сообщение, упоминания, голосовые и кружки; десктоп проигрывает голосовые и кружки; тесты правил покрывают новые поля; черновики не создают записей в Firestore.

## Этап 6.5. Готовность к настоящим пользователям

То, без чего приложение отклонят в App Store и Google Play или без чего оно сломается при первых десятках пользователей.

1. Блокировка и жалоба (правило Apple 1.2): `users/{uid}/blocked/{otherUid}`, правила запрещают заблокированному писать в личный чат и добавлять в группы, тесты правил; заблокированный чат пропадает из списка. Жалоба — документ `reports/{id}`, который читает только владелец проекта в консоли.
2. Удаление аккаунта в приложении (Apple 5.1.1(v), Google Play): удаляются профиль, устройства, `chatPrefs`, свои сообщения помечаются удалёнными, затем удаляется аккаунт Firebase на всех устройствах.
3. Минимальная версия: документ `config/app` с `minVersion` по платформам, экран «Обновите приложение». Нужен до того, как ужесточать `firestore.rules`, иначе старые клиенты ломаются молча.
4. Квоты Spark (20 000 записей и 50 000 чтений в сутки): heartbeat присутствия реже и только при открытом приложении, троттлинг «печатает…», расчёт расхода на одного активного пользователя в ARCHITECTURE.md.
5. Пагинация ленты: сейчас загружаются последние 300 сообщений, старые подгружаются при прокрутке вверх.
6. Политика конфиденциальности (страница на GitHub Pages) и описание Data Safety для Play.
7. Мониторинг лимитов. Spark не шлёт предупреждений, а бюджетные алерты Google Cloud требуют платёжный аккаунт, поэтому:
   - ежедневный GitHub Action забирает из Cloud Monitoring API чтения, записи и удаления Firestore за сутки (сервисный аккаунт с ролью только на чтение метрик, ключ в секретах репозитория) и падает выше 75% квоты — GitHub присылает письмо о красном прогоне. Сначала проверить, что Monitoring API отдаёт эти метрики на Spark без биллинга;
   - Caps & Alerts в B2 на 75% и 100% по хранилищу, скачиванию и вызовам классов B и C;
   - Worker считает за сутки загруженные байты и выданные ссылки на скачивание и отдаёт их на `GET /stats` только владельцу проекта; Action из первого подпункта добавляет их в тот же отчёт.
8. Уборка:
   - еженедельный GitHub Action (Admin SDK): сверяет файлы B2 с `attachment.key` в Firestore (запрос только по сообщениям с вложениями) и удаляет сирот — файлы, загруженные без отправленного сообщения; удаляет истёкшие `linkRequests`, старые «надгробия» удалённых сообщений и устройства, не заходившие дольше полугода. Удаления тратят ту же квоту (20 000 в сутки), поэтому уборка идёт порциями ночью. Уборка в Actions, а не в cron Worker: там проще держать ключ Admin SDK, а у бесплатного Worker короткий лимит CPU;
   - lifecycle-правило бакета B2 для старых медиа (срок — решение о продукте, например 180 дней); клиент показывает «Файл больше не хранится»;
   - на клиенте: лимит дискового кэша фото, голосовых и кружков (по умолчанию 500 МБ, вытесняются самые давние) и «Очистить кэш» в настройках с занятым местом.

**Готово, когда:** заблокированный пользователь не может написать (проверено тестом правил); аккаунт удаляется из приложения; старая версия видит экран обновления; при 50 активных пользователях в день расчёт укладывается в квоты Spark; превышение 75% любой квоты Firestore или B2 приходит письмом; файлы-сироты в B2 удаляются без ручной работы.

3. Дистрибуция: GitHub Releases, по желанию Google Play и TestFlight.
4. README: скриншоты всех платформ, схема архитектуры, протокол привязки, видео.
5. Бот Ghostlink — системный собеседник в списке чатов каждого пользователя. Нужны push-worker (6.2), счётчики и метрики из 6.5.7 и сборки в GitHub Releases (7.1). Cloud Functions нет, поэтому бот живёт в Worker: у Worker уже есть ключ сервис-аккаунта для FCM, с ним он пишет в Firestore через REST от имени бота в обход правил.
   - Чат `chats/bot_{uid}` с `type: bot`: пользователь пишет команды и нажимает кнопки под сообщениями бота, клиент после отправки вызывает `POST /bot`, Worker отвечает сообщением бота. Правила: пользователь пишет в этот чат только текст команд, сообщения от имени бота пишет только Worker; тесты правил.
   - «Лимиты»: расход Firestore, B2 и Worker за сутки в процентах от квоты, как в отчёте 6.5.7. Подробности видит только владелец проекта (`OWNER_UID` в секретах Worker), остальные — короткий статус «Фото и видео работают» или «Лимит на сегодня исчерпан, до 03:00».
   - «Скачать APK»: версия, размер, что нового и ссылка на APK последнего GitHub Release (через GitHub API, с кэшем в Worker). Сам файл в B2 не кладётся: 20–30 МБ на скачивание съели бы суточный лимит, а GitHub Releases раздаёт бесплатно. Кнопка есть только в Android-сборке для GitHub Releases: правила Google Play запрещают приложению из Play обновляться в обход Play, поэтому в сборке для Play её нет. На iOS вместо APK — ссылка на TestFlight, если он есть.
   - Новый релиз: CI из 7.1 пишет одно объявление в `botFeed/{version}` (читают все, пишет только CI), клиент показывает его в чате бота. Одна запись на релиз вместо записи в каждый чат бережёт квоту Spark.
   - Вид официального бота: чат создаётся сам при первом входе и закреплён вверху списка, у бота иконка-призрак и галочка ✓. Галочку получает только чат с `type: bot`, а такой чат и сообщения от имени бота клиент создать не может (правила + тесты правил), поэтому назваться «Ghostlink» можно, а получить галочку — нет. Чат можно заглушить или убрать в архив, но не удалить.
   - Бот пишет сам — по cron Worker (есть на бесплатном плане): отчёт о расходе за прошедшие сутки раз в день и предупреждение сразу при пересечении 75% и 100%. Расход B2 и Worker виден на каждом запросе, Firestore — из Cloud Monitoring API при запуске cron. Сообщение будит телефон через push (6.2).
   - Кто что получает: владелец — подробные отчёты и предупреждения в своём чате (одна запись на сообщение); остальные — только «Фото и видео временно недоступны» и «Снова работают» одной записью в `botFeed`, а не в каждый чат.
   - Ограничение: если исчерпана суточная квота записей Firestore, бот не может об этом написать, поэтому письмо о красном прогоне Action из 6.5.7 остаётся запасным каналом.

## Этап 8. Сквозное шифрование (E2E)

Ключ аккаунта уже одинаковый на всех устройствах (его передаёт привязка), поэтому из него выводится постоянная пара ключей аккаунта, и синхронизировать ключи между устройствами не нужно. Цена простоты — нет forward secrecy: утечка ключа аккаунта раскрывает всю переписку. Это не протокол Signal, и README должен говорить об этом прямо.

1. `core:crypto`: пара X25519 из ключа аккаунта через HKDF; публичный ключ в `users/{uid}.publicKey` + правила + тесты правил; test vectors для всех платформ.
2. Личные чаты: ключ чата = ECDH двух публичных ключей → HKDF; `text`, `replyTo.preview`, `pinnedMessage.preview`, `forwardedFrom` и `lastMessage` шифруются AES-256-GCM, id сообщения входит в AAD.
3. Группы: ключ группы создаёт админ и раздаёт участникам, зашифровав ключом личного чата с каждым; при удалении участника ключ меняется.
4. Вложения из этапа 6 шифруются на клиенте до загрузки в B2.
5. Проверка собеседника: код безопасности (отпечаток публичных ключей) в профиле, сравнение при встрече или по QR.
6. Переход: старые сообщения остаются открытыми и помечаются; push показывает «Новое сообщение» без текста.

**Готово, когда:** в консоли Firestore и в B2 нет открытого текста новых сообщений и файлов; переписка читается на всех платформах аккаунта; коды безопасности двух собеседников совпадают.

## Сознательные ограничения
- До этапа 8 нет сквозного шифрования (E2E), а в этапе 8 оно без forward secrecy.
- Нет звонков: для WebRTC нужен TURN-сервер, бесплатно надёжно не поднять.
- Отзыв отдельного устройства мягкий; жёсткий — только «выйти на всех устройствах» (смена пароля).
- На десктопе нет push, только уведомления запущенного приложения.
- Медиа живут в бесплатных лимитах B2: когда суточный лимит исчерпан, фото, голосовые и кружки не грузятся до следующих суток.
